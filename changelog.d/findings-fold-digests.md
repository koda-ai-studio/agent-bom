### Performance
- On PostgreSQL, the current findings view decodes and projects only scans whose stored row changed since it was last read. Before, any job write (including a push being admitted) made the next findings read decode every retained report again, so its cost grew with scan history and every reader waited for it. The overview's open-findings count reuses the same per-scan work. `AGENT_BOM_FINDING_WALK_CACHE=0` turns it off with the rest of the cross-request finding reuse.
- On Python 3.12 and later (the published images run 3.14), admitting a large push takes about a quarter of the CPU it did: the idempotency fingerprint encodes report sections with the C JSON encoder (same hash, one list element at a time), and the NaN/infinity check confirms finite sections in C instead of walking every value. A 109 MB, 500-agent report: fingerprint 8.1 s → 1.7 s, body validation 2.2 s → 1.2 s.
- Measured on one API process with PostgreSQL during a 500-agent ingest and 120 s of dashboard reads: findings p95 9.4 s → 4.6 s, overview p95 27.6 s → 5.0 s, no 503s (5 before), and 50% more requests served. Overview still rebuilds from every retained scan after each job write; that is the remaining stall.
