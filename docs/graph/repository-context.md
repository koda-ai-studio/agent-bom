# Repository workspace context

Run `agent-bom scan -p . --offline -f json -o report.json` to inspect a local project. The report includes `project_inventory.repository_context`: first-party package declarations, their source manifest digest, directory and recorded CODEOWNERS match. Import the report into the control plane and expand its repository directory in Investigation to inspect files, packages and findings. Workspace packages use code-module nodes with the `workspace_package` subtype; they do not count as third-party packages or MCP servers.

| Manager | Collected declaration | Local dependency links |
|---|---|---|
| npm / Yarn | Root `package.json` and declared `workspaces` members | Explicit `workspace:`, `file:` and `link:` declarations |
| pnpm | The same manifests plus `pnpm-workspace.yaml`, including exclusions | Explicit workspace and local-path declarations |
| uv | `[project]` and `[tool.uv.workspace]` members/exclusions | Explicit `[tool.uv.sources]` entries with `workspace = true` |
| Cargo | `[package]` and `[workspace]` members/exclusions | Explicit per-package dependency `path`; inherited workspace dependency resolution is not inferred |
| Go | Root `go.mod` and local `go.work` `use` members | Required module names matching an explicitly selected workspace member |
| Nx / Turbo | Underlying package-manager manifests only | Task graphs, generated projects and implicit dependencies are not collected |

A matching package name alone does not establish local resolution. Recorded third-party package inventory is reused only for the matching manifest, declared dependency and ecosystem. Files belong to the nearest unambiguous workspace directory; mixed-language directories without a unique owner stay unresolved. Finding membership follows existing finding-to-file evidence. Declared membership is static evidence, not proof of code execution or permission.

Repository IDs use a versioned digest of the resolved local root, entity kind and relative identity. They remain stable across rescans of that checkout, including after path redaction; separate checkouts have separate identities. These IDs are not an authorization boundary: authenticated tenant scope still controls persistence and reads. Legacy reports without repository context retain their original IDs. Current-estate projection format 6 rebuilds the current view; retained historical snapshots are not rewritten. No branch/ref identity is asserted when it was not collected.

Collection uses bounded local reads, rejects traversal and symlink artifacts, and does not execute package scripts or contact registries. Limits are 2 MiB per workspace artifact, 32 MiB of artifact reads, 10,000 enumerated directory entries, depth 12 and 500 package declarations. Dependencies and workspace patterns are bounded too. Unreadable, unmatched and limited inputs carry unresolved reasons and partial status. CODEOWNERS uses the existing last-match rule with its source path. Nested independent projects outside the declared workspace are not silently treated as members.

The existing directory roll-up is the first graph view; drill-down pages expose its children. Package source details and ownership remain available on selection. Coverage is limited to the primary project inventory in a multi-project CLI report; each project's third-party package inventory remains on its own existing carrier.

## dbt lineage

Place an existing `target/manifest.json` in the project before scanning. The scanner reads manifest schemas v8–v12 and retains model, source, seed and exposure names, source paths, directed `depends_on.nodes` relationships and the artifact digest. It does not run dbt, compile Jinja, execute SQL, retain SQL bodies or copy profile passwords. The field layout follows the [dbt manifest contract](https://docs.getdbt.com/reference/artifacts/manifest-json) and [v12 schema](https://schemas.getdbt.com/dbt/manifest/v12.json).

The primary project's manifest is limited to 16 MiB within the shared 32 MiB artifact budget, 2,000 supported nodes, 256 parents per node and 10,000 edges. Unsupported versions, invalid paths, missing parents and cycles carry explicit reasons. A generated timestamp older than seven days is stale at collection; missing, unzoned or future timestamps are unknown. This is artifact age, not a check that every source file still matches the compiled manifest. Historical snapshots retain their recorded state.

For Snowflake, optional local `profiles.yml` / `profiles.yaml` supplies only the selected profile/target's literal account identifier. Home-directory profiles and environment variables are not resolved. A warehouse correlation requires an authenticated graph tenant, the exact recorded account and three exact identifier components. Quoted case, embedded dots and significant spaces remain distinct. Unknown accounts, ambiguous object matches and non-current manifests do not produce warehouse correlations. Correlation edges are non-traversable and do not assert permission, execution or successful materialization.

Graph nodes are labeled `dbt model`, `dbt source`, `dbt seed` and `dbt exposure`, distinct from connector-reported warehouse objects. Existing dbt findings attach when the manifest identifies one unique resource for the finding's source file. A shared YAML file with several resources remains ambiguous instead of assigning the finding to every resource. Selecting a node exposes its artifact, collection state and connector-match result.

## Static pipeline and SDK context

The same scan reads `.gitlab-ci.yml` and literal repository-local includes. GitLab jobs retain declared `needs`, literal environment names and keys from the `secrets` section. Commands, variable values and secret-provider paths are omitted. Remote/project includes, wildcard or interpolated paths, inheritance and job overrides remain unresolved; no includes are downloaded. Local include paths follow the [GitLab repository-relative contract](https://docs.gitlab.com/ci/yaml/includes/), with traversal and symlinks rejected. Reads are limited to 256 KiB per YAML file, 32 included files, depth eight and 1,000 jobs.

Python syntax parsing recognizes literal Airflow `DAG` declarations, named operator/sensor assignments, `dag=` or a single DAG context manager, and `>>` / `<<` task dependencies. It retains literal connection-reference names. Loops, decorators, functions, generated DAGs and other dynamic structure remain unresolved. No DAG code is imported or executed. Cycles and duplicate task identities are partial evidence. The adapter follows the static declaration forms in the [Airflow DAG documentation](https://airflow.apache.org/docs/apache-airflow/stable/concepts/dags.html); it does not reproduce the Airflow scheduler.

Python files with named LLM, MCP, agent-framework or cloud SDK imports retain import aliases, source lines and bounded static call expressions. Literal local relative imports resolve only inside the nearest workspace boundary. A local module shadows a same-named external SDK. Reassigned or deleted bindings, dynamic imports, wildcard imports and unsupported control flow do not establish a call target. Call arguments, prompts and credential values are omitted. Recognized agent factory assignments appear as **Agent declaration** code artifacts, not observed agent workloads. Imports and static calls do not establish execution, access or permissions. JavaScript/TypeScript imports, dynamic resolution, external Python search paths and whole-program interprocedural analysis are outside this adapter.

Source enumeration is limited to 250 Python files within 10,000 visited entries and depth 12. Each file is at most 256 KiB and 20,000 syntax nodes, within the shared artifact-read budget. A file retains at most 64 imports and 100 call expressions. Pipeline context is bounded to 2,000 declarations and 10,000 links. The collector retains partial reasons when a limit is reached. Source artifacts and pipeline/import edges reuse directory roll-up; expansion and selection expose the details. Static pipeline and import edges are non-traversable for attack paths.

## Repository changes

Open **Changes → Repository changes** to compare workspace packages, dbt models and pipelines, with files receiving new finding links. Comparisons require complete matching source coverage, repository identity and branch/ref evidence on both snapshots. The collector reads only a local `.git/HEAD`, local branch refs and bounded `packed-refs`; it does not execute Git or follow external worktree `gitdir` files. It checks the ref again after collection. A missing ref, changed ref during collection, different branch, first observation or partial scan cannot establish a semantic removal. A Git revision records the checkout basis; it is not an assertion that the working tree is clean or identical to that commit.

Entity counts reuse the canonical snapshot diff. The response supplies at most 30 detail rows, while the drawer initially shows ten and links to the existing full paged diff. New finding-file details examine at most 500 added finding links and mark a truncated sample explicitly. Rows link to the snapshot that recorded the entity, including the previous snapshot for a removed entity. Reads bind both graph generations and discard the summary if either changes. No longer recorded does not mean remediated; historical graphs remain intact.
